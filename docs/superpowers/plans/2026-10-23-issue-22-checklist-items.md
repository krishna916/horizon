# Issue #22 — Lightweight Task Checklist Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Owner review gate:** This document is an implementation plan, not approval to start coding. Do not begin implementation until the owner approves this written plan and selects/preserves Luna's execution mode.

**Goal:** Let each task own an ordered, editable checklist with immediate completion and due-date changes, saved reordering, soft-delete with 8-second Undo, initial checklist creation, and a frontend-only unfinished-item warning when completing a parent task.

**Architecture:** Keep `Task` as aggregate root with task-scoped, owner-gated checklist commands; persist `ChecklistItem` children in a separate PostgreSQL table using Flyway and transactional sibling ordering. Return children only in detail representations, not list summaries. Add one reusable checklist view and a shared pre-completion gate in the React task feature; preserve the existing TaskCompletionProvider's optimistic and serialized behavior.

**Tech Stack:** Java 25, Spring Boot 4.0.6, Spring Data JPA, PostgreSQL 17, Flyway, Testcontainers, Maven; React 19, TypeScript, TanStack Query v5/Router, Axios, React Hook Form/Zod, TailwindCSS v4, Radix/shadcn, Lucide, Vitest/RTL, Playwright.

**Spec:** [Issue #22 approved design](../specs/2026-10-23-issue-22-checklist-items-design.md) (owner approved 2026-10-23). Also read [approved Tasks workspace design](../../design/tasks-workspace/DESIGN-SPEC.md), [issue #21 completion spec](../specs/2026-10-22-issue-21-task-completion-design.md), `docs/ai/HORIZON_DECISION_SUMMARY.md`, PRD-004 Tasks, PRD-002 Today and Horizon Constitution.

## Global Constraints

- Implement only after owner plan approval, on a dedicated `feat/issue-22-task-checklist` branch/worktree rooted at the committed design + plan, not directly on `master`. At execution time use `superpowers:using-git-worktrees` and the approved implementation mode; follow TDD and verification-before-completion.
- Follow root `Agents.md`, `client/AGENTS.md` and `server/AGENTS.md`; run repository `align-context`, `testing-spring-integration` and `testing-frontend` workflows. Check `docs/ai/INDEX.md` before changing APIs or schema. Respect `ENG-001` escalation when modifying API contracts and `ENG-002` client conventions.
- Modular monolith, `task`-owned behavior only. Ownership = authorization: query task by `id` + current `userId` + `deletedAt IS NULL` **before** accessing children. Cross-task and cross-user item IDs are inaccessible (`404`), not `403`. Archived tasks remain editable, deleted tasks do not.
- Persist lifecycle facts (`completed_at`, `deleted_at`), not a status enum. `checklist_item` table; `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `DATE` for item due date, `TIMESTAMPTZ` for lifecycle, `INTEGER` for position; Flyway SQL-first; Hibernate `validate` only.
- REST resources remain under `/api/v1/tasks/{taskId}/checklist-items` with dedicated request/response DTOs and RFC 9457 errors. Do not create a separate controller per action; one nested-resource `TaskChecklistController` is permitted and keeps `TaskController` focused.
- Parent `POST /api/v1/tasks/{id}/complete` stays **unconditional**. Its unfinished-checklist dialog is **frontend-only** and shown *before* calling the existing completion provider. Preserve #21's fast reversal, list retention, archived completion, field-draft independence, in-flight saving and Retry.
- Title max **255** characters after trimming. Item dates are optional `YYYY-MM-DD`, independent of task dates; saved immediately when chosen/cleared. Checkbox toggles persist immediately. Rename and reorder have explicit Save/Cancel.
- While an unsaved reorder session is active, **all other checklist mutations and parent-field editor activation are disabled**; existing task-parent completion/reopen remains independent. The existing guard supports only one draft registration; do not build a multi-draft system.
- Remove persists immediately by setting `deleted_at`. Show client-side Undo for **8 seconds** (also dismissed on leaving details); restore the original row/identity/data/position. No global Trash, timer on server, cleanup job, or notification infrastructure.
- Unfinished items retain their own Today eligibility when their parent is completed, but not archived or deleted. **Do not implement Today UI in this story.**
- Existing creation idempotency contract is mandatory: initial checklist children and task created in one transaction; identical key+normalized body replays without duplicates; changed checklist/order with reused key conflicts.
- Frontend server state belongs to TanStack Query, keyed by user and task. Use reusable detail components in `client/src/task/`, approved desktop visual baseline, accessible drag-and-drop with keyboard Up/Down move controls and announcements. Prefer **native drag events plus explicit keyboard Move Up/Down controls**, not a new dependency, for the currently desktop-only Tasks design; verify behavior in real browser Playwright.
- Required validation: backend Testcontainers/MockMvc under JVM UTC; frontend Vitest/RTL, Playwright, lint, typecheck, format and build. Preserve existing functionality and test coverage.

## Review Focus

These five risk cases must be tested where their responsible code is implemented, not merely checked at the end:

1. **Stale reorder** after another item was added/removed: exact live set must be validated; `409` without losing any item. Foreign/other-user item ID remains `404`.
2. **Repeated removal/restore and adjacent changes**: Undo returns same ID/completed timestamp/due date at deterministic position without duplicate active rows; stale client Undo must not restore a newer unrelated deletion.
3. **Ambiguous task-create retry** with ordered initial checklist: same owner/key/body returns one task and one set of children; modified initial child/date/order with same key conflicts.
4. **Parent completion from list** with task details uncached or failing: fetch on demand; no pre-dialog optimistic completion; failed checklist read is retryable and does not complete the task.
5. **Cross-user navigation/async result**: pending item commands or stale responses from one owner/task cannot mutate the cache or draft of another owner/task after switching surfaces.
